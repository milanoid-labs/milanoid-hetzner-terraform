# Hetzner (OpenTofu)

OpenTofu configuration for milanoid-labs' Hetzner resources. Today that's one
[Storage Box](https://www.hetzner.com/storage/storage-box/): the off-site target for the family photo
library on the Synology NAS ([homelab-cluster#872](https://github.com/milanoid-labs/homelab-cluster/issues/872)).

Synology **Hyper Backup** writes an encrypted, multi-version backup to the box over rsync/SSH
(port 23). It's a versioned backup, not a mirror, so files deleted or encrypted on the NAS
don't overwrite older versions. Hyper Backup itself is configured by hand in DSM.

The versions alone don't protect against a compromised NAS. The NAS holds the subaccount's
credentials, and that account can write, so whoever controls the NAS can delete every version.
That's why the box takes **daily snapshots** (the last 10 are kept). Only the main account or the
API can create or delete snapshots, and the NAS has neither.

## Layout

| File | Manages |
|---|---|
| `storage_box.tf` | Storage Box `nas-backup` (BX11, 1 TiB, `fsn1`, daily snapshots), subaccount `synology` (home `synology/`), their passwords |
| `outputs.tf` | Host and username for Hyper Backup's destination form; the subaccount password (sensitive) |
| `terraform.tf` | Backend and providers (`hetznercloud/hcloud`, `hashicorp/random`) |

Hyper Backup logs in as the subaccount, which only sees `synology/`. The main account's
credentials never go on the NAS, and the main account has SSH and external access turned off.

Deletion guards, because this box holds the NAS's only off-site copy:
- Hetzner `delete_protection` blocks deletion in the Console and API. It does **not** stop
  tofu: the provider turns it off by itself before deleting.
- `lifecycle { prevent_destroy = true }` fails a plan that would destroy or replace the box.
  It only works while the resource block exists.
- `Tofu Apply` refuses any saved plan that destroys or replaces an `hcloud_storage_box`. This
  covers a removed or renamed block. To retire a box on purpose, delete it by hand in the
  Console first.

Snapshots only hold what changed (ZFS), so a mostly-append photo backup costs little extra
quota. Snapshots count against the 1 TiB, though, so watch usage in the Console.

State lives in S3 (`milanoid-labs-terraform-tofu-state`, key
`milanoid-hetzner-terraform/terraform.tfstate`). It holds both passwords, so access to it is
limited to this repo's CI roles, which are managed centrally in
`milanoid-labs-terraform/bootstrap/aws-oidc/tofu_repos.tf`.

## Credentials

The hcloud provider reads `HCLOUD_TOKEN`. There are two API tokens for the Hetzner project
`milanoid-backup`, both created by hand in the Hetzner Console:

- **Read & Write:** repo secret `HCLOUD_TOKEN`, used only by `Tofu Apply` on `main`.
- **Read only:** repo secret `HCLOUD_TOKEN_READONLY`, used by `Tofu Plan` on PRs. A PR plan runs
  PR-branch code, including Renovate provider bumps, before anyone reviews it. With this token,
  that code can't change or delete anything.

In both workflows, only the tofu steps get a token, not the third-party actions.

Locally: [direnv](https://direnv.net/). `.envrc` (committed, no secrets) clears any inherited
`HCLOUD_TOKEN`/`AWS_PROFILE`, then loads `~/.config/milanoid-hetzner-terraform.env`
(mode 600) with `dotenv`:
```sh
HCLOUD_TOKEN=...            # R/W
HCLOUD_TOKEN_READONLY=...
AWS_PROFILE=milanoid
```
Run `direnv allow` once after cloning.

To rotate a token, create a new one in the Console, update the repo secret and the env
file, then delete the old token.

The Storage Box passwords are generated by `random_password` and live only in state. To
rotate the subaccount password, run `tofu apply -replace=random_password.synology`, then
update it in Hyper Backup.

## Workflow

PR → `Tofu Plan` posts the plan as a PR comment → merge → `Tofu Apply` on `main`.
`main` is protected by a ruleset (PR required), managed in `milanoid-labs-terraform`.
CI runs on `homelab-runners`, like the other tofu repos.

## Local use

```sh
direnv allow
tofu init
tofu plan
```

## Hyper Backup setup (DSM)

The NAS side is configured by hand in DSM (Hyper Backup → **+** → Data backup task). If you
ever need to recreate it, use these settings. Values in `<…>` come from `tofu output`.

**Destination**

| Field | Value |
|---|---|
| Destination | File Server → **rsync** |
| Backup version type | **Multiple versions** |
| Server type | **rsync-compatible server** |
| Server name | `<synology_server>`, the `-sub1` host, **not** the main account's |
| Transfer encryption | On |
| Port | **23** |
| Username | `<synology_username>`, the `-sub1` user |
| Password | `tofu output -raw synology_password \| pbcopy` |
| Backup module | type **`/home/`** by hand |
| Directory | `nas2-photos` (a single name, no `/`). Hyper Backup creates `nas2-photos.hbk` |

Things that went wrong the first time:
- **The password manager autofills the main account** (`u…` without `-sub1`). The main account
  has SSH off, so that login fails with "Failed to establish the SSH connection".
- **The Backup module dropdown stays empty.** Hyper Backup lists modules from the server's root,
  and the subaccount is locked into its own folder, so listing `/` is denied. Type `/home/`
  yourself. `home` without the slashes fails with "Failed to connect to the backup destination".
  ([Hetzner's tutorial](https://community.hetzner.com/tutorials/synology-hyperbackup-to-storagebox)
  says the same.)
- **The main account doesn't need SSH or external access.** The subaccount's own
  `access_settings` are enough.

**Source:** `photo`, and each person's `homes/<user>/Photos`. Expand `homes` and tick only the
`Photos` folders, never `homes` as a whole. The dedup quarantine (`homes/<user>/_duplicates-quarantine`)
sits outside `Photos`, so it stays out. No applications.

**Settings:** notifications on, compression **off** (photos and videos are already compressed),
schedule daily 01:00, integrity check weekly on Sunday 04:00, **client-side encryption on**.

**Rotation:** Smart Recycle, 120 versions. That's about a month of daily versions, then weekly
ones going back about 2 years. Versions share unchanged data, so the history costs little quota.

**Encryption secrets:** the encryption password and the `.pem` key DSM offers at the end of the
wizard. Keep both outside the NAS (password manager plus a paper/USB copy). See [Restore](#restore).

The first upload of about 425 GB ran at about 12 Mbit/s, which took about 3 days.

## Restore

You need the Hyper Backup **encryption password** and its **`.pem` key**. Both are kept
outside the NAS, in the password manager plus a paper/USB copy. Without them the backup
can't be decrypted, and Hetzner can't recover them.

- **The `synology/` folder was wiped or damaged:** in the Console, Storage Box → Snapshots,
  roll back to (or browse) a snapshot from before the damage, then continue below.
- **NAS still working:** in DSM, Hyper Backup → the task → **Restore** → Data. Pick a version,
  then choose the folders or files.
- **NAS lost:** on a new Synology, install Hyper Backup → **Restore** → Data → "rsync-compatible
  server" with the subaccount's host and username (`tofu output`), port 23. Pick the existing
  backup task and enter the encryption password, or use the `.pem` key.
- **No Synology at all:** download the backup over SFTP (`sftp -P 23 <synology_username>@<synology_server>`),
  then open the `.hbk` folder with **Hyper Backup Explorer** (Windows/macOS/Linux). It decrypts with
  the password or `.pem` and lets you browse versions and copy files out.

Test a restore every 6 months (homelab-cluster#879).
